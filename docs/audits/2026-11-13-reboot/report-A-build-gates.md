# InitechOS build/test forensic report A

Investigation date: 2026-11-13. Repository: `/home/tobiasosborne/Projects/InitechOS`. Measured revision: `b571f1e35cc386803ccd763f427c1cabe41866b9` (2026-11-06, worklog/WL-0195 addendum). This report is read-only. No compilation, tests, gates, emulator runs, checkout changes, commits, or pushes were performed. All investigation output was written in the authorized scratchpad. Initial status contained the pre-existing untracked `.beads.gate.lock`; another process was building, so ignored build artifacts were not treated as a stable snapshot.

**The current system is larger than the figures in the question:** 1,740 active vector entries (941 nominal host + 799 emulator), 1,961 defined `test-*` names, 352 named kernel links, and 555 expanded image targets. These are different measures; none means “1,740 independent checks” or “555 images constructed on every run.”

**Assessment:** retain the oracles, reference fixtures, and tools; restructure ownership, invalidation, and execution. Moving the same global dependency graph into smaller makefiles would improve navigation but would not make merges cheap. The costly boundaries are shared kernel links and addresses, universal invalidation, shared writable test state, and certification policy.

**C2 — expanded make database, without recipe execution:**

```sh

make --no-print-directory -qp -o build/flair_dac.stamp.mk test-kernel-headroom > "$S/headroom-db.txt" 2> "$S/headroom-db.err"
```

`-q` is deliberately safer here than `-n`: recursive recipe lines can execute under `-n`. The inert `gate-map-inventory-db` target is the repository's own inventory-probe target ([harness/gate_map.mk:23](/home/tobiasosborne/Projects/InitechOS/harness/gate_map.mk:23)). Parse-time `$(shell ...)` sites were inspected first; these probes perform reads/arithmetic and, for headroom, another `-qp` database query. Both stderr files were empty. A successful database print is not a successful build/test. The first database was 95,346 lines / 8,067,080 bytes. The command tool reported about 0.26 s elapsed for that probe; this is incidental observation, not a controlled parse benchmark.

**C3 — actual counting and selector emulation:**

```sh

```

This small script only reads the checkout/databases and writes under `$S`. It strips `define ... endef` bodies from the *variable* portion of the database before reading canonical `TEST_*_GATES`; otherwise template assignments can overwrite the real vector in a naive parser. It inventories targets only from the `# Files` section, matching the rule in [harness/gate_map.mk:30](/home/tobiasosborne/Projects/InitechOS/harness/gate_map.mk:30). It reads expanded prerequisites, excludes `%` pattern targets for concrete-artifact counts, and maps gate ownership from `spec/gate_map.json`. Path matching ports [tools/gate_map.c:170](/home/tobiasosborne/Projects/InitechOS/tools/gate_map.c:170) using libc `fnmatch(..., FNM_PATHNAME)` and the same special handling of `**`. It checks that each inventoried gate has exactly one owner. It does not run `make gates-for` or `make test-gate-map`, because those commands write in `build/` and/or run gates.

## 4. Coupling: gates-for / test-for

## 8. Five structural reasons a small change is expensive to land

1. **Validation is broad by construction rather than by component boundary.** Existing calc and i123/core files select 1,909 names; window selects 1,809; int21 selects 1,856. The resolver promotes a single path match to an entire family, and sources are repeated across families to cover shared consumers. This is measured selector behavior, not a guess from Makefile size ([tools/gate_map.c:809](/home/tobiasosborne/Projects/InitechOS/tools/gate_map.c:809), [spec/gate_map.json:209](/home/tobiasosborne/Projects/InitechOS/spec/gate_map.json:209), `:241`, `:1086`). Also, emitted targets may include non-default optional gates. The selector's current correctness contract is conservative coverage, not minimal affected testing.

2. **A global invalidation mechanism and variant-wide size policy defeat incremental isolation.** Root Makefile or any SAMIR `.def` registry change reaches every one of 1,740 entries via a common stamp. Headroom builds all 352 kernel bins, with a recorded 245-variant run costing ~15 min. The 269 `_mut` kernel names dominate the variant set. These guarantees have value, but they are presently paid as whole-repository work ([Makefile:73](/home/tobiasosborne/Projects/InitechOS/Makefile:73), `:459`, [docs/worklog/WL-0168-kernel-size-round-5.md:267](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0168-kernel-size-round-5.md:267)).

3. **Execution state is shared and repeated, making cheap parallel scheduling hard.** Serial `test-unit`/`test-emu` loops launch a new make per gate; mutants/aggregates can rerun positive gates. Two independent makes can race on fixed images/logs/scratch. The sharded certificate pays for multiple fresh worktrees and per-worker builds to avoid that; one-make parallel paths need explicit pair ordering and freezing of nested producers ([Makefile:31891](/home/tobiasosborne/Projects/InitechOS/Makefile:31891), [Makefile:31905](/home/tobiasosborne/Projects/InitechOS/Makefile:31905), [harness/gate_pairs.mk:3](/home/tobiasosborne/Projects/InitechOS/harness/gate_pairs.mk:3), [tools/cert-sharded.sh:125](/home/tobiasosborne/Projects/InitechOS/tools/cert-sharded.sh:125), [harness/merge_samir.mk:76](/home/tobiasosborne/Projects/InitechOS/harness/merge_samir.mk:76)). Bochs adds a host-global serialization point. This is a dependency/state ownership problem, not lack of CPU cores.

4. **Integration is encoded in links and compile-time scenarios, including address-bound imports.** There are 121 kmain object builds, 137 conditional openings in a 400 KB source file, 352 kernel links and hundreds of image rules. Shared kernel ABI flags, LTO and imported transient/overlay symbols connect managers, DOS services and GUI shell state. A “test variant” is often another whole link/image rather than a case passed to a stable guest runner ([Makefile:822](/home/tobiasosborne/Projects/InitechOS/Makefile:822), `:838`, `:10828`, `:10984`, `:11008`). A frozen ABI at component boundaries would change this cost model; a directory rearrangement would not.

5. **Landing requires reproducible and reference-valid evidence across several environments and process stages.** Almost half the active names are mutant-tagged; repro gates deliberately redo clean builds; host-vector pubs can boot emulators; reference snapshots live in private sibling repositories and missing tools fail loud. Certificates are bound to exact base/head and coverage, while proof replay/sentinel/culprit can create further builds. Recorded hidden dependencies, stale captures and cross-machine path/ROM problems cause rework as well as runtime ([Makefile:35016](/home/tobiasosborne/Projects/InitechOS/Makefile:35016), [pubs/pubs.mk:446](/home/tobiasosborne/Projects/InitechOS/pubs/pubs.mk:446), [tools/cert-check.sh:29](/home/tobiasosborne/Projects/InitechOS/tools/cert-check.sh:29), [docs/HANDOFF.md:286](/home/tobiasosborne/Projects/InitechOS/docs/HANDOFF.md:286)). The exact number of review/certification iterations per landed change is unmeasured, so this is an explanation of mechanisms, not a quantified claim about total human review hours.

The source-file size contributes navigation, conflict and maintenance cost. It is not demonstrated to be the main runtime bottleneck: the safe database probe was subsecond, while the recorded big costs are emulator replay and repeated links/builds. The source itself includes multiple stale claims; that is an additional documentation maintenance cost, not evidence that all current gates are invalid.

## 9. What survives a component/frozen-ABI restructure

A sensible partition would retain a thin root orchestration layer for a few integration/system tests, image packaging, compatibility matrices and release certification. Components would own source lists, exact dependency files, local host tests, output directories and explicit ABI contracts. A common immutable artifact/cache store and unique per-test scratch would permit parallel scheduling without per-gate rebuild namespaces. Those are architectural inferences, not changes made in this investigation.

**Inherently whole-system today:** real-mode boot/geometry/placement, interrupt/EXEC/loading/TSR interactions, shared kernel-size ceiling, LTO-linked kernel/manager composition, FLAIR's composed event pump/screen state, address-derived transient/overlay tables and their byte-repro tests. These should remain a smaller explicit integration/release layer; there is no honest way to make a boot-chain correctness oracle a pure local calc unit test. They are “inherently monolithic” relative to the present runtime architecture, not an assertion that the OS can never be refactored.

**Must change to realize the benefit:** the universal stamp, giant per-kernel object lists and repeated source-link commands, test behavior baked into kmain/preprocessor flags, broad whitelist family promotion, mutable shared scratch names, and duplicate recursive gate execution. The fixed ABI must decouple *links and test execution*, not only source directories. Address-based `--just-symbols` and generated overlay imports would need a stable export/versioning strategy or continued explicit relink integration tests ([Makefile:10931](/home/tobiasosborne/Projects/InitechOS/Makefile:10931), `:10984`, `:11008`).

**Not established by this investigation:** current gate pass/fail state, current wall time, coverage sufficiency, byte identity across named variants, a measured speedup for a proposed redesign, or that restarting the build system from scratch would be cheaper than incremental restructuring. The evidence supports keeping valuable independent oracles while replacing the machinery that couples them; it does not support discarding them and rebuilding their ground truth.
