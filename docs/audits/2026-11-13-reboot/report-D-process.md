# InitechOS process forensics: where the effort went, June–November 2026

Research D · read-only repository study · 2026-11-13

**Finding:** the project has substantial product output, but integration became a shared, repeatedly invalidated job. Parallel lanes consume the same kernel budget, Makefile namespace, fixture volumes, reference corpora and host resources. The PM then repairs and re-proves the composition. As validation grew from tens to roughly 1,500–1,700 gates, its cost reduced full-suite cadence; independent sweeps consequently found old regressions. The response was usually another gate, size round, re-mint or procedural rule. Several recent changes address the causes, but the final worklog still blocks every future kernel-growing lane on another capacity round.

### What a small change must do at the current HEAD

A normal successful v2 path comprises **about 12 stages**, several containing multiple commands:

1. Ground the task; obtain current main and an isolated lane with correct absolute corpus paths.
2. Add/identify the independent failing oracle; record RED at a named SHA.
3. Implement, run the required gates and meaningful mutants; commit.
4. Refresh the lane against the current integration base and resolve conflicts.
5. Run `lane-cert.sh`: derived gate selection, gate execution and named verdict checks.
6. Assemble RED/GREEN/MUTANT replay records and the BRANCH/COMMITS/CERT/NOT PROVEN report.
7. Independent review; fix findings and repeat affected proof/certification if necessary.
8. PM runs `cert-check.sh <cert> <lane-ref>`; exact lane head and local main base must match.
9. PM/verifier replays the proof manifest; reviewer verifies that this happened.
10. Make one no-ff merge including required code/spec/golden changes together.
11. Smoke/re-gate the integrated main, push, and record issue/worklog/handoff state. Keep the lane branch until certification.
12. Run local sentinel: selected gates and then sharded certificate, failure isolation and culprit/revert handling if needed.

This is a successful-path stage count, **not a claim that every tiny typo has 12 unique commands**. Root CLAUDE Rule 7 still allows direct trivial/small edits, whereas the new merge policy says one lane per merge and no code between merges. That unresolved policy tension itself invites escalation. Optional PM-authorized subsets and `LANE_CERT_JOBS=1..8` can reduce repeated work, but need explicit scope and metadata; the default lane-cert path is serial gate invocation.

The certificate text is explicit: “**Advancing main makes the old cert stale: rebase, rerun gates, regenerate the pack.**” If N lanes certify the same base and main advances through them one at a time, up to N−1 lanes immediately need another certification; lanes that repeatedly miss their turn can do more. This is structural duplication, not evidence that developers were slow at coding.

## 5. The kernel size saga: repeated byte recovery instead of lasting capacity

### Physical bottleneck versus retained process targets

The early kernel lived below the application image. Later it moved high, but stage2 still loaded it through a **196,608-byte real-mode bounce buffer** before copying it above 1 MiB. A 1 MiB execution runway does not enlarge that disk-to-memory transfer buffer. ADR-0014 says directly: “**The binding constraint is the stage2 load window, not RAM.**”

There have been several different caps:

- Original low-memory overlap boundary: kernel end versus `PROGRAM_BASE`, including BSS.
- Bounce/window capacity: **196,608 B**, physically meaningful for the selected loader layout.
- All-kernel safety floor: **4,096 B** under that window.
- Round-3 arrival/reclaim cap: **172,492 B = 182,732 − 10,240**, retained after its originating round. **Retired October 24** as a nonphysical target.
- Flagship round-4 floor: **16,384 B**, i.e. loaded bytes ≤ **180,224**.
- ADR-0014 overlay resident target: **169,984 B = 196,608 − 4,096 − 2×11,264**, reserving two worst-case feature slices as well as the safety floor. This is the binding current **policy** cap, not the maximum addressable RAM.

Conflating these limits is how a temporary success criterion can become an indefinite feature tax. [WL-0181](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0181-retire-r3-cap.md) explicitly says the old r3 criterion “**cannot govern every subsequent feature**.” The matching SAMIR reclaim clause was retired in [WL-0182](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0182-retire-samir-size-reclaim-clause.md), while its physical PAL-memory floor stayed.

## 6. What worked, and why

1. **June foundation delivery was fast and tangible.** The June 8–9 subjects progress through boot/FAT, SFT/JFT, console I/O, shell, FAT writes and positioned multi-handle I/O. June has **95,347 OS-line churn versus 88,468 machinery**, better than the later ratio. This is greenfield output, so it cannot prove the same pace was sustainable at mature scope. But the short dependency chain and relatively small aggregate made “verify after each landing” affordable. [WL-0010](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0010-Test-Aggregate-and-Multi-Tenant-File-IO.md) identifies a simplification: “**The SFT was already the handle table**”; per-handle positions replaced a more elaborate buffer-pool idea.

2. **SAMIR's PAL boundary supported low-conflict parallel product development.** [WL-0030](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0030-SAMIR-M6-Phase1-codec-plus-Phase3-core-plus-Phase4-open.md): “**Two lanes edited the tree concurrently for 5 waves with zero conflict**.” Each owned disjoint files, compiled private host binaries and left Makefile integration to one owner. The session completed the DBF codec and core evaluator and opened indexing; host gates increased 104→124 without adding emulator legs because the PAL isolated OS dependence. One real linking dependency was caught by the aggregate. That is productive independent checking without shared-tree mutation races.

3. **Bounded correctness batches produced useful returns.** [WL-0068](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0068-samir-p1-correctness-cluster.md) cleared 12 pre-identified P1 issues plus an integration-discovered oracle defect through seven file-owned lanes. Five finished cleanly; two needed rate-limit takeovers, so it was not friction-free. The positive pattern is pre-grounded faults, local ownership and explicit integration, not the model brand or number of agents.

4. **Reference-first feature batches sometimes delivered a lot in one session.** [WL-0104](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0104-the-frontier-night.md) records **15 lanes in the 00:00–05:10 session**, including 123 formulas/menu operations, Word P1, control keys and Restart/Shut Down, with **eight reproducible clips**. The formula work checks **1,090 corpus formulas and 986 cached results**. It had real integration friction and a size round, so it is not a low-friction control period; it shows that concrete, externally grounded product work can coexist with disciplined checking when the queue remains short.

5. **Fixing the factory's mechanisms beats adding compensating retries.** Guest acknowledgments and completion markers, separate mutable fixtures, one-producer rules, Bochs locking, recorder lockstep and source-only publication lockstep delivered measurable results. [WL-0190](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0190-merge-velocity-fanout.md) reports three cold greens, ~114–119-second vectors and **37/37 byte-identical clips**. The sharded certificate cut five hours to 66m45s and exposed real undeclared dependencies. These are genuine speed and confidence gains.

6. **The November 6 one-hour experiment isolated the opportunity cost of constraints.** [WL-0195](/home/tobiasosborne/Projects/InitechOS/docs/worklog/WL-0195-dec03a-workflow-v2-oneshot.md) reports six coders, **42 minutes**, roughly **8/10 W4 apps** at a relaxed bar, 16/16 emulator legs, 49 screendumps and a ~42-second replay. It found the keyboard bug and empirically demonstrated that 54 KB of UI would not fit the old app window. Its private SAMIRX memory hack and reduced authenticity/acceptance obligations make it **not release-ready and not an apples-to-apples productivity benchmark**. The claimed “5–10× at ours” is the orchestrator's estimate, not a measurement. Still, it helped prompt a concrete architecture/acceptance change instead of another blind shrink loop.

The common success factors are **stable interfaces, bounded scope, independent references available before implementation, private mutable state and integration capacity matched to lane count**. There is no evidence that removing all oracles would preserve product quality: June's masked loader bug and November's 249/529 index failures argue strongly against that interpretation.
